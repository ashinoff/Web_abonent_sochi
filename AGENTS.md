## 1. Зачем существует проект

- **Репозиторий:** https://github.com/ashinoff/Web_abonent_sochi
- **Происхождение:** независимая копия https://github.com/ashinoff/Web_abonent
- **Цель:** реестры абонентов, потребление, журналы ПУ, поиск, аналитика и офлайн-доступ для Сочинского предприятия электрических сетей.
- **Изоляция:** исходный `Web_abonent` не изменять без отдельного прямого задания. Автосинхронизация исходного репозитория с сочинским удалена. Не копировать изменения вслепую: в исходнике другая схема источников данных.
- **Развёртывание:** отдельное приложение и **отдельная** PostgreSQL-база; не переиспользовать базу первого приложения из-за пересечения таблиц.
- **ВНИМАНИЕ:** оставшийся в репозитории `PROJECT_CONTEXT.md` унаследован от первоначального `Web_abonent` и описывает в основном старую архитектуру с Яндекс Диском. Для Сочи первичны **этот файл, текущий код и README.md**.

## 2. Неприкосновенные требования владельца

**Предприятие только одно:** `Сочинское предприятие электрических сетей`. Выбора других предприятий нет.

**Семь РЭС, строго в таком составе:**

1. Адлерский РЭС
2. Краснополянский РЭС
3. Хостинский РЭС
4. Сочинский РЭС
5. Дагомысский РЭС
6. Лазаревский РЭС
7. Туапсинский РЭС

Единый источник истины для названий, путей и ролей: `public/sochi-config.js`.

**Порядок работы:**

1. **Администратор** заводит учётные записи, назначает пользователям видимость одного или нескольких РЭС. Сервер проверяет разрешения на **каждом** запросе, а не только прячет кнопки.
2. **Только администратор** загружает файлы XLS/XLSX с **компьютера через браузер**, отдельно для каждого РЭС. Типы: реестр (`registry`, «Расширенный список»), потребление (`consumption`, «ПО»), приём (`incoming`), мгновенные параметры (`instant`, журнал 31), события (`events`, журнал 46).
3. **Никакого Яндекс Диска** и автоматического импорта из внешних папок в сочинском сервере. Пользователь не загружает исходные Excel, не выбирает чужие источники.
4. Подготовленные данные, статусы файлов, учётные записи и параметры анализа хранятся **в PostgreSQL**. При ошибке загрузки предыдущая рабочая версия пакета остаётся. Большой Excel разбирает отдельный ограниченный процесс.
5. **Обычный онлайн-пользователь** получает только необходимые результаты поиска, карточки и анализа по API. Не скачивать весь реестр при каждом открытии РЭС или запросе.
6. **Только администратор** меняет фильтры, пороги, чувствительность и алгоритмы анализа. Эти параметры централизованно хранятся в БД и применяются к онлайн-расчётам, а не доверяются параметрам клиента.
7. **Офлайн:** сотрудник может явно скачать подготовленные пакеты только своих РЭС на телефон; данные хранятся в IndexedDB, разделённые по учётным записям. Без связи доступен локальный поиск и анализ по сохранённым данным/настройкам. Для полного Excel-отчёта допустимо получить полный подготовленный пакет отдельно.

## 4. Важные ограничения и риски

- В сочинском варианте обязательны `SUPER_ADMIN_LOGIN`, `SUPER_ADMIN_PASSWORD` и `DB_*`; `YANDEX_PUBLIC_URL` **не нужен**. Секреты никогда не коммитить в Git.
- Использовать отдельную БД и не смешивать учётные записи и снапшоты Сочи с основной системой.
- Проверять `resPath` и роль **на сервере до чтения данных**, в том числе при выборе каталога, карточки, анализа, уведомлений и офлайн-пакета. Скрытие интерфейса недостаточно.
- Замена книги должна быть атомарной; при ошибке разбора не удалять старые подготовленные данные. Исходный Excel не хранить в репозитории и удалять временную копию на сервере.
- Пакеты Excel и индексы могут быть большими; следить за RAM Amvera, нагрузкой одновременных пользователей и SQL. Не возвращать полный реестр на каждый запрос. Предельный размер загружаемой книги в текущем коде — 80 МБ, **это не гарантия**, что любой такой файл пройдёт лимит памяти.
- При правке файлов веб-оболочки проверить версию кэша `public/service-worker.js` и полноту списка офлайн-модулей. Изменения офлайн-логики проверять на **реальном телефоне**, включая повторный вход и отсутствие сети.
- Настройки онлайн-анализа обязательно из БД; локальная копия для офлайна может быть устаревшей. При смене методики продумать уведомление и обновление скачанных пакетов.
- Уже сохранённую на отключённом устройстве копию невозможно немедленно отозвать через сервер. Не обещать мгновенную отзывчивость офлайн-доступа.
- **На 23.10.2026 развёртывание на отдельной Amvera, работа на реальных больших выгрузках Сочи и тестирование на физических телефонах не подтверждены.** Наличие коммита и зелёной CI не считать доказательством боевого запуска.

## 6. Журнал изменений и решений (пополнять сверху вниз)

### 2026-10-23 — Шаблоны Excel, расширенная админка и анализ ошибок базы

- **Запрос владельца:** пять скачиваемых XLSX-шаблонов, широкая модалка настроек на ПК, настройки **только для администраторов**, серьёзная группировка административных разделов и отдельный анализ ошибок базы.
- **Excel-шаблоны:** `sochi-template.mjs` формирует XLSX с правильной шапкой и одной заведомо вымышленной строкой для каждой из ролей `registry`, `consumption`, `incoming`, `instant`, `events`. У журнала 46 строго три столбца. Для реестра и журналов номера ПУ/ЛС сохраняются текстом. Перед реальным импортом образец **обязательно заменить**.
- **API:** `GET /api/admin/template?role=...` доступен только с ролью `admin`/`superadmin`; сотрудники получают HTTP 403. В `sochi-server.mjs` отклонённый импорт теперь дополнительно фиксируется кодом `upload_failed` в админском журнале (без сохранения исходного файла в БД), чтобы видеть причину в «Анализе базы». Замена ранее принятого пакета остаётся атомарной.
- **Настройки и офлайн:** `public/index.html`, `public/styles.css`, `public/app.js`, `public/account-ui.js`, `public/analysis-ui.js`, `public/admin-ui.js`. Только администраторы видят и открывают окно `#settings-dialog`. Для сотрудников перенесён **тот же** интерфейс `#load-map-settings` в `#offline-dialog`: можно сохранять только свои РЭС и выходить из системы через отдельную кнопку. ID элементов и алгоритм офлайна не дублируются.
- **Визуальный интерфейс:** увеличенное окно при ширине >=900 px, структурированные блоки «Загрузка и шаблоны», «Учётные записи», отдельная вкладка **«Анализ базы»** с анализом 35 статусов, пропущенных обязательных реестров/ПО, ошибок и журналом действий. Незаполненный *необязательный* журнал не маркируется ошибкой.
- **Тесты:** `tests/sochi-template.test.mjs` проверяет распознавание реальными парсерами и потоковым XLSX-импортом; `tests/sochi.test.mjs` проверяет HTTP и доступы; `tests/sochi-ui.test.mjs` — роль сотрудника; `tests/sochi-admin-ui.test.mjs` — шаблоны, загрузку и диагностику. Сверять результат CI последнего коммита, не считать коммит успешным тестированием до окончания прогона.
- **Ограничение:** `incoming` пока только валидируется и сохраняется; балансный алгоритм не существует. Шаблон — формат входных данных, а не реализация расчёта.
- **Amvera:** изменения сделаны в GitHub; факт публикации на Amvera, новая БД и испытание на реальных крупных Excel ещё не подтверждены.
